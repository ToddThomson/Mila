Get started

Four ways in, all ending at the same place: a model answering you on your own GPU. They differ in who you are, not in what you get — pick the tab that describes you.

C++I'm building a C++ app PythonI'm building in Python DockerI want a ready-made development environment CloneI want to read or contribute to Mila
{{/* ── C++ — the default panel when no tab is targeted ──────────────── */}}
What you get
A model answering prompts, from your own CMake project.
What it costs
A C++23 toolchain, CUDA, and a from-source build of Mila. Budget for the first one.
1

Declare the dependency

include(FetchContent)
FetchContent_Declare(
    Mila
    GIT_REPOSITORY https://github.com/ToddThomson/Mila.git
    GIT_TAG        v0.20.0-beta.2
)
FetchContent_MakeAvailable(Mila)

add_executable(my_app main.cpp)
target_link_libraries(my_app PRIVATE Mila::Mila)

Pin a tag, not a branch — Mila is pre-1.0 and breaking changes are expected. Your project compiles all of Mila, every CUDA kernel included, so set CMAKE_CUDA_ARCHITECTURES to your own GPU's arch; the default multi-arch list compiles every kernel several times over.

2

Load a model and generate

// A module import, not a header.
import Mila;

Mila::initialize();

// The store is the only source -- loading never downloads.
auto installed = ModelStore{}.locate( "gemma-4-12b-it-fp4" );
auto tokenizer = BpeTokenizer::loadGemma( installed->tokenizer_path );

GemmaModelConfig config( 4096 );
config.withFP4Quantization();

// Device and precision are template arguments: the type IS the configuration.
auto model = GemmaModel<DeviceType::Cuda, TensorDataType::BF16>::fromPretrained(
    installed->weights_path, config );

// The model owns the decode loop and pushes each token to your callback.
auto status = model->generate( prompt_tokens, [&]( int32_t id ) {
    std::cout << tokenizer->decode( std::span( &id, 1 ) ) << std::flush;
}, params );
3

Run it

./build/mila_quickstart "Why is the sky blue?"
Mila 0.20.0-beta.3
Loading gemma-4-12b-it-fp4 ...

The sky appears blue because of a phenomenon called Rayleigh
scattering, where the atmosphere's gases and particles scatter
shorter blue wavelengths of sunlight more effectively than longer
red wavelengths. This scattering occurs in all directions, causing
the entire sky to take on a blue hue.

[stop]

You end up with a local LLM answering prompts inside your own C++ application — no execution engine, no runtime dispatch, your main().

{{/* ── Python ───────────────────────────────────────────────────────── */}}
What you get
A model answering prompts, and a script you can take apart.
What it costs
A pip install and a model download. No compiler.
1

Install Mila

pip install mila-llm

A compiled extension carrying its own CUDA. Python 3.12 or 3.13, on Windows or Linux.

2

Install a model

import mila
mila.initialize("warning")
mila.ModelStore().pull("gemma-4-12b-it-fp4", mila.default_hub_owner())

Roughly 6.3 GB, ungated — no account, no access request, no token. Pull and load are separate verbs, so nothing downloads behind your back later.

3

Talk to it

python quickstart.py "Why is the sky blue?"
Loading gemma-4-12b-it-fp4 ...

The sky appears blue because of a phenomenon called Rayleigh
scattering, where the Earth's atmosphere scatters shorter
wavelengths of light more effectively. Because blue and violet
light waves are shorter, they scatter more across the atmosphere,
making the sky appear blue to our eyes.

The same program as the C++ tab — same model, same template, same defaults — so the two read side by side with only the language differing. Standard library only: no framework underneath it.

You end up with Gemma 4 streaming in your terminal, plus chat.py for multi-turn and two more scripts covering sampling and the store.

{{/* ── Docker ───────────────────────────────────────────────────────── */}}
Not published yet. Both tags are still local, so the commands below start working the day the images ship. Sizes are estimates until a publish build is made.
What you get
A configured Linux environment with Mila already compiled: the library, the source, the samples, Chat, the inference server and the C++23 toolchain. Your host can be Windows or Linux.
What it costs
Docker — on Windows, Docker Desktop with the WSL2 backend. Then one download of roughly 12 GB, and an NVIDIA GPU.
1

Start the environment

docker run --gpus all -it -v mila-store:/models \
  toddthomson/mila-llm:0.20.0-beta.3-devel

You land in a shell, in a Mila tree that is already built. Your host supplies the GPU driver through the NVIDIA Container Toolkit; on Windows, Docker Desktop with the WSL2 backend provides it.

2

Install a model

mila install gemma-4-12b-it-fp4

About 6.3 GB, ungated. The volume keeps it, so every later run starts with it in place.

3

Write your own program against Mila

cd ~/myapp        # a CMake project, already configured
vim main.cpp      # import Mila;
cmake --build build

./build/myapp "Why is the sky blue?"

Mila is already compiled in that build tree, so your first build takes seconds — the same program on your own machine costs a C++23 toolchain, a CUDA install and a 15-minute build of Mila first. What you get is a Linux binary; to build for Windows, use the C++ tab.

You end up with every part of Mila working — your own program linking it, the chat harness, and an HTTP endpoint on port 6452.

{{/* ── Clone ────────────────────────────────────────────────────────── */}}
What you get
All of it — the chat harness, the tests, the samples, and the source you came to read.
What it costs
A C++23 toolchain, CUDA, and a full build.
1

Clone and build

git clone https://github.com/toddthomson/mila.git
cd mila
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build

Ninja, not MSBuild — C++23 modules need it. On Windows, open the folder in Visual Studio 2026 instead and pick a preset.

2

Run the chat harness

./build/ChatApp

/models --online          what is published
/install gemma-4-12b-it-fp4

Chat opens on an empty store, so a first run with nothing installed still reaches /install.

You end up with the most complete thing Mila has — streaming, tool calls, model switching — and the source that produced it.

Install a model

{{/* --rm on both commands: the model lives in the volume, so the container is disposable, and without it every run leaves a stopped one behind until `docker image rm` fails on a conflict the reader has no context for. The Docker TAB deliberately omits it -- that image is an environment the reader edits, not a disposable one. */}} 
docker run --rm --gpus all -v mila-store:/models \
  toddthomson/mila-llm:0.20.0-beta.3-runtime install Llama-3.2-3B-Instruct-fp4

2.87 GB — the smallest instruct model Mila publishes, ungated. The volume keeps it, so every later run starts with it in place.

2

Talk to it

docker run --rm --gpus all -it -v mila-store:/models \
  toddthomson/mila-llm:0.20.0-beta.3-runtime chat --model Llama-3.2-3B-Instruct-fp4
{{/* The model is named rather than inferred from a store that happens to hold one: Chat switches models at runtime, so a command that guessed would change meaning the moment a second model was installed. The reasoning stays here -- a reader running the command has no question for it to answer. */}}

You end up with Llama 3.2 answering on your own GPU — the same library the C++ and Python tabs build against, with no toolchain on your machine.

This tag runs models and nothing else. To write your own program against Mila, Get started ships the full environment — a different CUDA base, so it is a separate download rather than a top-up.
